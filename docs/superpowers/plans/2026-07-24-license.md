# Open-Source License + IP Separation — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an OSI-style open-source license for the project's own code (the
Python firmware, the JS web twin, build tooling, tests, and design docs this
repo authors), while making it structurally impossible to misread that license
as covering the two things it must not: the generated card database the build
pipeline compiles from third-party sources, and the Lord of the
Rings/Fantasy Flight trademarks and copyrighted text the app displays.

**Not a legal opinion.** This plan is written by an AI assistant, not a
lawyer. It recommends a license and drafts the text a maintainer would
plausibly want, but the underlying legal questions (fair use, trademark fan-use
tolerance, what a court would do with an unlicensed community TSV) are not
resolved by anything here. Where the plan says "recommend," read it as
"reasoned default, not adjudicated fact."

## Important — a risk finding surfaced during research

Before the license comparison: research for this plan turned up a fact that
bears directly on the project's overall posture, not just on which SPDX
identifier goes in `LICENSE`. It doesn't change the recommendation below (code
license and IP exposure are separate axes — see "Why this doesn't get fixed by
a license" at the end of this section), but the user should see it, because it
is more specific than what informed the original card-data-pipeline decision.

Fantasy Flight Games' parent, Asmodee North America, publishes a "Guidelines
for Community Use of Our Intellectual Property"
(<https://images-cdn.fantasyflightgames.com/filer_public/51/c8/51c8035b-240e-4a12-8ab6-a7b34b97c819/ip_policy_2024_aug20.pdf>,
dated 2024-08-20; verified by downloading and running `pdftotext` on it during
this research — full text is 98 lines, not paywalled or access-gated). It
permits most "Fan Creations" (fan sites, homebrew scenarios, alternate art)
under conditions (non-commercial, credited, not appearing affiliated, no
"substantial amount" of copied game materials) — but one guideline is
unconditional:

> "6. Do NOT make Apps. For licensing and other business reasons, we simply
> cannot allow our intellectual property in software applications of any
> kind — whether or not they follow all of the other rules in these
> Guidelines."

Two caveats that keep this from being a clean verdict, both straight from the
same document:
- The policy explicitly covers only FFG/Asmodee-owned IP (game mechanics,
  FFG's own text/design). It says plainly it cannot speak for IP owned by
  others bundled into their games — and names *The Lord of the Rings*
  specifically as one of those others (Middle-earth Enterprises owns the
  Tolkien trademarks; FFG holds a license from them, per this project's own
  About-screen text). No equivalent published Middle-earth Enterprises fan
  policy was found during this research.
- "Software application" is exactly what this project is (web twin + Presto
  firmware), and it does compile FFG's own game-system data (turn sequence,
  phase structure, the full card database including card text) into that
  application — this isn't a stretch reading, it's what `tools/build_card_data.py`
  does. Search for a public enforcement action against a comparable
  companion-app project turned up a real, on-point precedent in the
  *Lord of the Rings* space — Middle-earth Enterprises sent a cease-and-desist
  to the *LOTRO* private-server project "Echoes of Angmar" in August 2022
  (<https://massivelyop.com/2022/08/05/middle-earth-enterprises-sends-cease-and-desist-letter-to-lotro-rogue-server-project/>)
  — but nothing was found specifically against DragnCards, Hall of Beorn, or
  RingsDB, all of which occupy roughly this project's niche and have operated
  publicly for years. Absence of evidence of enforcement against comparable
  projects is not evidence of tolerance; it's just what a web search surfaces.

## Architecture

Three new/changed files, no code changes:
- `LICENSE` at repo root — canonical OSI license text, unmodified.
- `NOTICE` at repo root — this project's own text: copyright line, scope
  carve-outs (what `LICENSE` does *not* cover), consolidated third-party
  disclaimer, and provenance pointers. Apache-2.0 gives `NOTICE` files
  formal standing (§4(d): a work that includes a NOTICE file obligates
  redistributors to carry its attribution notices forward) — one more reason
  Apache-2.0 fits this project's specific "keep the boundary visible even to
  someone who forks and redistributes" need.
- `README.md` — a new short "License" section pointing at both files.

## Tech Stack

Plain text (`LICENSE`, `NOTICE`) and Markdown (`README.md`). No code, no
build step, no tests to add — `python3 -m pytest tests/` is unaffected and
does not need to be re-run for this plan, though running it once at the end
costs nothing and confirms nothing else was disturbed.

## Context

TODO.md "Ideas": *"Choose an appropriate license, fully open source but with
care regarding the copyrighted IP."* `ROADMAP.md`'s wishlist already names the
same want: *"An open-source license (careful with the copyrighted IP)."* No
license exists today — confirmed by listing the repo root; there is no
`LICENSE`/`LICENSE.md`/`COPYING` file, so by default-copyright operation of
law the code is currently all-rights-reserved even though the repo is public
(GitHub's own licensing guide is explicit about this:
<https://docs.github.com/articles/licensing-a-repository>) — visitors can view
and fork per GitHub's Terms of Service, but have no license to reuse the code.
That's the gap "fully open source" closes.

The card-data pipeline (`tools/build_card_data.py`, `tools/build_icons.py`,
`tools/build_hob_enrichment.py`, `tools/build_tips.py`) fetches from four
third-party sources and compiles/summarizes their content into
`docs/data/*.json`. All four outputs are **gitignored and never committed**
(verified: `git check-ignore` and reading `.gitignore` confirm `docs/data/`,
`tools/data/hob_cache/`, `tools/data/enrichment.json`, `tools/data/tips_cache/`
are all excluded) — so the license question for this repo's *tracked content*
is narrower than "does this project have the right to redistribute FFG's card
text," which is a question the existing design spec already answered with a
disclaimer-and-provenance mitigation, not a license. What a code license
*can* do here is (a) open the tracked source under permissive terms, and
(b) carry the existing mitigation language forward wherever the code goes,
via `NOTICE`.

One more piece of tracked content needs the same carve-out treatment as the
generated data, and it's easy to miss because — unlike `docs/data/` — it
*is* committed: `git ls-files` confirms `assets/boxart_480.png`,
`assets/boot_bg.png`, and `docs/assets/boot_bg.png` are tracked, not
gitignored. Per `README.md`'s own description these are "pixelated Revised
Core Set box art" — a cropped/downsampled derivative of Fantasy Flight's own
product photography (see the Done-column TODO entry "Crop boxart source to
480x480," commit `d83b997`). These three files are the one place in the
tracked repo where a blanket "this repository is licensed under Apache-2.0"
statement would, read literally, appear to cover something it has no right to
cover. `docs/screenshots/*.png` (also tracked) are different in kind — they're
screenshots of this project's *own* UI (layout, copy, iconography choices),
which are original work product even though the game terms ("Threat,"
"Willpower," quest names) appear as text within them; they don't need the same
carve-out, though the NOTICE language below is written broadly enough to cover
them too out of caution.

## Global Constraints

- **No implementation beyond the three files this plan describes.** Do not
  touch `tools/build_card_data.py`'s `DISCLAIMER` constant or any other code —
  it already emits its own (shorter, data-file-appropriate) disclaimer and is

  word-for-word identical (verified by reading both) — that's the canonical
  UI-facing disclaimer text; `NOTICE` should match it rather than invent new
  phrasing.
- **`python3 -m pytest tests/` must still pass** (Iron rule #3) — trivially
  true here since nothing code-shaped changes, but confirm at the end anyway.

### Task 1: Add `LICENSE` (Apache-2.0)

**Files:**
- Create: `LICENSE`

**Interfaces:** None — static text file.

**License comparison (the reasoning behind the recommendation):**

The three usual defaults, compared on the axes that matter for *this*
project specifically — a solo-maintained hobby companion app, currently
zero outside contributors, explicitly seeking a Contributing.md and outside
contributions (see the sibling plan), built for a fixed-purpose niche
(a specific card game on a specific piece of hardware), with no patent-bearing
technology and one live IP-boundary concern that a NOTICE file — not the
license grant — has to carry:

| | MIT | Apache-2.0 | GPL-3.0 |
|---|---|---|---|
| Type | Permissive | Permissive | Strong copyleft |
| Patent grant | None — permission to use only, patent rights unstated | Explicit, irrevocable patent license from every contributor, with a patent-litigation retaliation clause (terminates if you sue over the work) | Explicit patent grant, same copyleft-litigation protections as Apache |
| Contributor/downstream friction | Lowest — "copy this file, keep the notice" | Low — same, plus "state changes you made" and carry forward a NOTICE file if one exists | Highest — any distributed derivative must itself be GPL-3.0 and ship/offer complete source |
| Formal NOTICE mechanism | No | Yes (§4(d)) | No (informal notices only) |
| Best fit when | Library/tool where maximum adoption matters more than anything else | MIT's freedom plus patent hygiene and a place to put attribution/scope text | The goal is specifically to stop closed-source/commercial reuse of derivatives |

Sources: <https://choosealicense.com/licenses/mit/>,
<https://choosealicense.com/licenses/apache-2.0/>,
<https://choosealicense.com/licenses/gpl-3.0/> (GitHub's own license-picker
reference site, fetched directly for this plan) — corroborated by a second
pass of search results describing the same patent-grant distinction
(Apache's Section 3 explicit patent grant + retaliation clause vs. MIT's
silence on patents).

**Applying that to this project's actual criteria:**
1. *Outside contributors are an explicit goal* (Contributing.md is being
   added alongside this) → favors permissive over copyleft; GPL-3.0's "your
   PR's derivative must also be GPL" is friction with no corresponding
   benefit for a project this small.
2. *No patent-bearing technology* (a MicroPython/vanilla-JS companion
   tracker) → Apache's patent grant isn't solving an active threat, but it's
   free — zero added friction over MIT for either the maintainer or a
   contributor, and standard modern practice ("MIT plus patent hygiene") for
   exactly this reason.
3. *Copyleft's actual selling point — stopping a company from silently
   absorbing the code into a closed product — doesn't fit this project's
   realistic reuse profile.* The plausible forks are hobbyists adapting it
   for their own Presto, their own card game, or borrowing a UI pattern —
   audiences copyleft mostly inconveniences, not deters.
4. *The NOTICE mechanism is the deciding factor given this specific ask.*
   The user's brief is "open source, but careful with the IP" — Apache-2.0 is
   the only one of the three with a license-defined, tooling-recognized place
   (`NOTICE`, §4(d)) that formally travels with the code and must be carried
   forward by redistributors. MIT/GPL projects can informally add a
   `NOTICE.md`, but nothing in either license requires it to survive a fork;
   Apache's does.

**Recommendation: Apache License 2.0.** It's the license criterion 4 points
at directly, and criteria 1–3 don't argue against it.

**If the user prefers MIT instead:** drop Task 2's NOTICE-file framing down to
an informal `NOTICE.md` (nothing licenses it to survive a fork, but it's still
useful documentation) — everything else in this plan is unchanged; MIT and
Apache-2.0 are compatible and the choice mostly matters for the patent clause
and the NOTICE mechanism, not for anything else here.

**If the user prefers GPL-3.0 instead** (e.g., the real priority is "nobody
should be able to build a closed commercial product on top of this," not
contributor-friction minimization): use GPL-3.0's canonical text in Task 1
instead, keep Task 2's `NOTICE` file (GPL doesn't formally require one, but
nothing stops adding it), and expect it to measurably raise the bar for
outside contributions the Contributing.md plan is trying to lower — a real
tradeoff, not a defect in GPL-3.0, just the one this project's stated goals
argue against.
