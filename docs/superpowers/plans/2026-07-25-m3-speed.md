# M3 · Speed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cut a common round's tap count by making the three slowest interactions fast — inline threat ± directly in the players-zone cell (no modal), a direct willpower-total entry that mirrors the already-shipped staging control, and a one-tap "confirm all" for willpower commits — while retiring the redundant `CommitModal` cycling flow it replaces. *Done when* a scripted common round hits the tap budget defined below (22 taps, down from today's 29 for the identical scenario).

**Architecture:** Reuse the inline-± visual/interaction language already shipped for the staging-area cell (thin inset dividers + tan `-`/`+` glyphs, a non-modal tap) in two more places: (1) the players-zone threat token, which requires widening that zone from a 32px to a 48px per-player column stride so each half clears the ≥24px touch-target rule — the progress zone gives up the same 36px, dropping its worst-case side-quest headroom from 9 to 8 columns; (2) the "Questing for" totals-row cell, which gets the identical treatment `game.staging` already has, backed by the existing (already-shipped, currently staging-only) `wp-`/`wp+` aggregate handlers and a new `CounterModal`-based direct-total editor. Separately, `PlayersDetailModal` (shipped in M1) already supersedes `CommitModal` per `design/stats-redesign.md`'s own note that it "may be retired" — this milestone finishes that: delete `CommitModal` and its lone entry point, and give the freed screen space in Questing (Commit) to a new one-tap `confirm_all_commits()` action.

**Tech Stack:** ES modules (web, Canvas) + MicroPython (firmware); pytest + the scene layout linter.

**Context:** This is roadmap milestone **M3 · Speed** (`design/roadmap.md`): *"inline threat −/+, direct willpower total, one-tap all-players; declutter commit. No tap-and-hold. Note on "declutter": decluttering doesn't move this table by itself — `PlayersDetailModal` was already the fastest *existing* path for the P3 edit. What it removes is a slower, easy-to-stumble-into duplicate: tapping the (undifferentiated, silently-tappable) note panel opened the old per-player `CommitModal` cycling flow, which would cost 6 taps for this same edit (open + Next + Next + step+Next + Done) with no way to skip players who didn't change. Removing that trap, and giving the freed space to a clearly-labeled one-tap "Confirm all commits" action, is what turns the 6-tap "confirm everyone else" cost in today's table into 1 tap in tomorrow's.

## Global Constraints

- **Two twins in lockstep** (Iron rule #1): web `docs/js/` implemented first in each task, then mirrored to the firmware (`gamestate.py`, `ui/`). Identical button ids, geometry, and behavior.
- **`python3 -m pytest tests/` stays green** (Iron rule #3), including the layout linter (`tests/test_layout.py`). Add/update a scene per changed or new visual state.
- **Touch targets ≥ 24px in each dimension** (`tests/test_layout.py` `MIN_TARGET = 24`, checked independently per button — `b.w >= 24 and b.h >= 24`); the linter does not check button-vs-button overlap, but this plan never relies on ambiguous overlap between two *different* actions — only non-overlapping tiles, or a specific button layered in front of a broader catch-all.
- **Button hit-testing is first-match-wins in list order** (`main.py:301-304`, `docs/js/main.js:161-168`, confirmed): a more specific button must be appended to `self.buttons`/`this.buttons` *before* any broader catch-all it overlaps.
- **No tap-and-hold anywhere** (roadmap M3 line) — every new control in this plan is a plain single tap.
- `tools/gen_web_data.py` is **not touched** — this milestone changes no phase/icon/metric data, only layout and interaction code.
- **No rules-text changes** — nothing in this plan asserts a new game-rules claim, so no rulebook/FAQ verification is triggered.
- `game.willpower` and `game.staging` are **aggregate fields**, not re-derived from per-player state when edited through the totals row. `game.staging` has no individual components to desync. `game.willpower` normally equals `sum(p.commit for p in players)` (kept true by `set_commit`), but the existing `quest_staging` steppers (`wp-`/`wp+`, already shipped) already edit it directly without touching any player's `commit` — this plan extends that same, already-accepted aggregate-edit precedent to the Questing (Commit) view; it does not change the invariant's status. Per-player precision editing remains `PlayersDetailModal`'s job.
- `game.staging` is **not reset between rounds** (only `commit_touched` is) — it is a running total the player maintains, not a per-round transient.
- The players zone and progress zone remain **fixed-width regions** regardless of live player count / side-quest count (existing design philosophy — preserved, not changed).
- Screen is 480×480; `MARGIN = 8`; `HEADER_H = 40`; `ZONE_TOP = 46`; `CONTENT_Y = 150` — all **unchanged** by this plan except the internal split of the players/progress zones.

### Task 1: Inline threat ± in the players zone

**Files:**
- Modify: `docs/js/screen_play.js:34-96` (`_playersZone`, `_progressZone`), `docs/js/screen_play.js:554` onward (`onButton`)
- Modify: `ui/screen_play.py:56-120` (`_players_zone`, `_progress_zone`), `ui/screen_play.py:589` onward (`on_button`)
- Test: `tests/test_screen_play.py` (new + modified tests below)

**Interfaces:**
- Consumes: `game.adjust_threat(index, delta)` (existing, `gamestate.py:205-213` — clamps at 0, sets `pending_elim` on a fresh elimination; unchanged by this task).
- Produces: new button ids `("threat", i, -1)` / `("threat", i, 1)` on `ScreenPlay` for `i` in `0..len(game.players)-1`. New players-zone geometry: 48px-wide per-player columns (`pcx = [32, 80, 128, 176]`, absolute screen x), zone width 192 (was 156). New progress-zone geometry: divider at x=204 (was 168), content/button start at x=210 (was 174), button width 262 (was 298), `max_cols = (472 - 210) // 32` = 8 (was 9).

**The layout problem, solved concretely:** a single player's threat needs an independent minus *and* plus target, each ≥24px wide — 48px minimum, with no slack, since two 24px targets side by side can't fit in less. The existing 32px column stride is 16px short per player (4 players × 16px = 64px short overall). There's no vertical room to make up the difference instead: the threat token's own vertical band (between the P# header row and the willpower row) is under 30px, nowhere near the 48px two-stacked-24px-targets would need, and growing zone height would push `CONTENT_Y` down and ripple into every other view. So this task **widens instead of stacks**: player columns move from a 32px to a 48px stride (zone width 156→192, +36px), and the progress zone gives up those same 36px (298→262px usable, `max_cols` 9→8 — the *existing* overflow logic already drops the newest side quests gracefully when columns run out, so losing one column of theoretical headroom is a bounded, low-risk trade. This only bites at 8+ simultaneous side quests, which no LOTR LCG scenario currently in the catalog has). Each player's 48px column then splits cleanly into two contiguous 24px halves — tap the left half of the token for `-1`, the right half for `+1` — with a 1px vertical divider through the token center as the visual hint (the same "thin divider" language the staging cell already uses). No separate glyph is added per player (there's no collision-free room for one without further crowding the P# row above); a single dim `-`/`+` legend could be added at the zone's outer edges later if playtesting shows the gesture isn't discoverable — that's a copy-only follow-up, not a layout change.

*If the user prefers a different trade instead:* dropping `MAX_PLAYERS` support in the zone from 4 to fewer visible columns was considered and rejected (this app supports up to 4 players and the zone is explicitly designed to show fixed columns regardless of live count); relying on overlapping-but-technically-legal button regions (the linter only checks per-button size, not overlap) was also considered and rejected as genuinely ambiguous UX, not just a lint-dodge.

def test_common_round_hits_tap_budget():
    hw = FakeHardware()
    pal = Palette(hw.display)
    game = GameState()
    for i, c in enumerate((3, 4, 2, 2)):          # last round's persisted commits

        if isinstance(result, tuple) and result[0] == "modal":
